# Agent 上下文管理实验计划

> 状态：暂缓独立执行。优先推进 [Agent 能力复刻路线](agent-capabilities-roadmap.md)，在真实功能测试中观察窗口压力，再按本计划选择必要的实验。

## 目标

以现有的“项目内文档问答与编辑”链路为样本，学习 LangChain / LangGraph 如何控制模型输入，并比较策略对正确性、工具调用和 token 用量的影响。先记录基线，再逐步引入消息裁剪与摘要；每一步都保留可回退的对照结果。

本阶段聚焦现有 Agent，不扩展原 Java Backend 的外围功能。LangGraph PostgreSQL checkpointer 保持默认关闭；它可用于后续中断恢复实验，但不承担上下文压缩。

## 当前基线（待测量）

- `app/repositories/session_repository.py` 从业务会话表取最近 30 条已完成的用户/助手文本消息；这不是 token 预算，跨轮工具事件也不在这 30 条中。
- `app/services/agent_service.py` 将历史与当前消息交给图。启用 checkpointer 时，后续轮次改由图恢复消息状态，不再重复注入业务历史。
- `app/agent/nodes.py` 为每次模型调用附加系统指令和当前文档的 ID、标题、版本等信息；文档正文由 `document_read` 按需读取。
- 当前有每轮最多 6 个工具批次、`document_read` 单份文档最多读取 80,000 字符等保护，但没有按模型 token 窗口进行裁剪或摘要。
- 文件上传链路现支持 PDF、DOCX、TXT、Markdown、JSON：原件存于私有 R2，解析文本按约 2,500 字符分片存于 PostgreSQL。`file_content_read` 每次最多读取 5 个分片；模型收到的是附加文件的 `cache_key`，正文通过工具按需进入当前轮上下文。

以上是代码现状，不代表已经测得上下文节省或重复读取的数量。

## 固定任务与记录项

只使用临时账号和合成 Markdown 文档。每组任务固定初始数据、用户请求、模型和温度等可控参数；模型输出仍可能有随机性，必要时重复运行并记录差异。

| 场景 | 必须验证的行为 |
| --- | --- |
| 简短文档问答 | 正确读取当前项目文档，且不调用写入工具 |
| 长对话中的早期约束 | 多轮之后仍遵守用户先前明确保留的编辑约束 |
| 多次读取同一文档 | 记录相同文档版本被读取的次数，观察是否存在可避免的重复读取 |
| 较长 PDF 的首尾定位 | 使用合成的多页文本 PDF，通过分片窗口找到前后页的信息，不预先传入全文 |
| DOCX 结构与重复窗口 | 检查 Pandoc 保留的标题/列表，并记录同一 `cache_key + start_index` 被读取的次数 |
| 外部更新后的编辑 | 旧版本保存返回 `40903`，不能覆盖较新的草稿 |
| 跨项目文档 ID | 工具拒绝越权读取和写入 |

每次运行记录：模型 ID、输入/输出 token（提供方返回时）、送入模型的消息数、工具名称与次数、按 `document_id + version` 以及 `cache_key + start_index + limit` 统计的重复读取、每次返回的分片/字符数、耗时、文档最终版本、任务是否完成。只把必要的指标和结论写入实验报告，不把 API Key 或完整私人文档内容写入日志。基线可以先使用现有 `scripts/check_agent_flow.py`、`scripts/check_file_flow.py`、`tests/test_agent_graph.py` 和新增的合成场景。

## 实验顺序

### 1. 建立基线

给模型节点与工具执行增加轻量指标采集，先运行上述固定任务。保存原始指标表和失败案例，确认当前 SSE、会话回读、权限及版本冲突行为。

### 2. 只裁剪模型输入

在 `app/agent/nodes.py` 调用模型前使用 LangChain 的 [`trim_messages`](https://docs.langchain.com/oss/python/langgraph/add-memory#trim-messages) 按近似 token 预算选择消息。原始 `session_messages` 与图状态不因这一步而删除。裁剪必须保留当前用户请求，不能留下没有对应结果的工具调用；对长文档工具结果要单独检查预算效果。

### 3. 评估摘要是否必要

若裁剪导致早期约束丢失，再尝试把较早轮次提炼为短摘要，保留近期完整消息。摘要可记录目标、已确认的约束、决策和产物 ID；写入前的文档版本必须重新从业务数据读取，不能只相信摘要。先在合成任务上比较，再决定是否需要为摘要增加持久化字段或表。

### 4. 对照与取舍

把“当前基线 / 裁剪 / 裁剪加摘要”的任务完成情况、token 用量和工具调用放在同一张结果表中。只有在正确性和权限边界保持成立后，才考虑将某种策略设为默认；不预设节省百分比。若收益不明显，保留最简单的方案。

## 验收标准

1. 五类固定任务都有可复现的输入、结果和指标记录；失败样例能指出丢失了哪段必要上下文。
2. 引入策略后，现有登录、工作区、签到及 Agent 联调脚本继续通过；Web 的流式工具事件与刷新回读仍正常。
3. Agent 的保存仍须经过项目权限、同轮成功读取和 `version` 检查；摘要或裁剪不能成为绕过这些规则的理由。
4. 结论明确区分“实际测得的变化”和“仍待验证的预期”。

完成此实验后，再单独评估写入前人工审批的 `interrupt` / `resume`。该实验需要开启 checkpointer，可参考 [checkpointer-experiment.md](checkpointer-experiment.md)，不与上下文裁剪混为一项功能。
